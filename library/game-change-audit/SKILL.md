# 游戏改动审计

先明确本次要支持的决定，例如能否送审、改动是否符合规格、哪些问题应返修。直接点名或宿主出现这些审查任务时使用。审计强度随影响与证据调整，沿宿主原验收和owner边界交付。

## 固定审查对象

读取当前任务、批准规格及必要例外，绑定被审的提交、文件哈希或构建。正在变化的产物先固定只读快照，收尾核对是否仍是当前版本。保留旧评审，与修后结果分别记录。

列清实际读取、实际操作和未覆盖的范围。审查包优先包含改动前后、当前完整相关实现、真实状态与需求理由。只拿到截图时，可以判断截图里的问题，动态规则和输入行为保持待验证。

## 选择检查面

根据当前风险只加载命中部分。每个已选择的面都需要具体状态、产物与判断依据。

| 当前任务 | 重点与专业联动 |
|---|---|
| 规则、数值、经济或构筑改动 | 前置条件、支付与结算、顺序、叠加、例外和利用路径，读[规则与运行审查](references/rules-and-runtime.md) |
| UI、图标、角色、动画或资源包审阅 | 实际尺寸、语义、状态组合、图文对应和真实消费者，读[界面与资源审查](references/interface-and-assets.md) |
| 操作、暂停、生命周期、联机或性能 | 用上表规则分支明确不变量，按具体缺口调用可用的game-runtime-patterns或宿主引擎方法 |
| 体验或设计合理性仍有争议 | 先描述受影响的玩家判断与已批准取舍，按需用game-decision-support补经验或安排真实试玩 |

可用的interaction-design负责操作与状态方案，game-presentation负责资源生产与交付，game-feel负责反馈配方。复现需实际操作时使用宿主QA或可用game-playtest；原因不明确时组合systematic-debugging。观察入口本身受阻才调用feedback-loop。只加载当前缺口，技能缺失时继续审查可取得的证据并说明边界。

## 检验发现

从玩家动作或资源使用场景追到实际结果。代码疑点用正常入口复现，静态图里的问题用原尺寸图和对应层/数据定位。将每项判断归为以下一种。

- **确认问题**，违反明确规格或可核验行为，给出触发状态、期望与实际、受损目标、证据和影响级别的理由。
- **合理取舍**，行为符合已批准条件，记录代价及适用范围。
- **改进建议**，属于设计或体验偏好，写明收益假设与验证方法。
- **待验证**，缺少运行、来源或状态证据，说明哪一项检查能区分解释。

视觉审查同时检查元素之间的关系。用户指出压边、对齐、可读性、残底或叠加问题时，读取界面分支的“边界、对齐与叠层”，按实际显示尺度重新核对受影响状态，逐张已看与检查充分程度分别记录。

主动找一个会推翻疑点的条件，例如某个修饰器本来就改写默认规则，禁用态有明确原因，文字由真实控件动态覆盖。复查替代解释后再定级。清单中的“通过”须对应实际证据，图片加载、代码运行和真实体验分别下结论。

## 交付与复核

优先报告能改变本次决定的问题，使用宿主原问题/审阅记录。每项带资源或规则ID、版本、复现步骤或图中位置、判断依据、影响与最小修复方向。合并同根因，标明已知问题、重复发现、新增发现和未覆盖范围；无确认问题也保留覆盖说明。

修复后验证对应失败已消失，并检查相邻正确状态是否保留。活跃生产者继续拥有实现和采用决定；本审计结果交原owner处理，技术检查通过、视觉自审、制作人采用与引擎安装分别记录。

## 方法效果需要比较时

仅在评估本方法、其他审查策略或重大流程变更时读取[效果校准](references/calibration.md)。日常审计直接检查实际任务，沿用现有评测入口，避免每次审计都启动盲评。
